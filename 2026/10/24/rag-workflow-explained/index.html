RAG 检索增强生成工作流程详解

1. 什么是 RAG

RAG（Retrieval-Augmented Generation，检索增强生成）解决的是这类问题：大模型参数里的知识有截止日期，也不包含你的私有文档、内部 Wiki、最新业务说明。

做法可以概括成一句话：

先把文档变成可检索的向量存起来；用户提问时，先检索相关片段，再把「问题 + 相关文档」一起交给 LLM 生成回答。

这样回答更能锚定真实资料，也能降低「凭空编造」的概率，并便于标注出处。

2. 总览：一张图看清两条主线

下图把 RAG 拆成上下两块：Indexing（索引入库） 与 提问后的 Retrieve / Generate（检索与生成）。

读图时抓住三点：

  1. 上方虚线框 Indexing：文档 → 解析 → 分块 → 嵌入 → 写入 Vector store，通常离线完成。
  2. 下方在线链路：User 的 query → 同样经 Embedding Model 向量化 → 检索 Vector store → 得到 Relevant docs → 与 query 组成 prompt → LLM Generate → response。
  3. Embedding Model 与 Vector store 被两边共用：建库和查询必须处在同一套语义空间里。

3. Indexing：离线建索引

Indexing 是后台预处理。用户提问之前，知识库就应准备好（也可定期增量更新）。

3.1 Docs：原始文档

起点是各类原始材料，例如：

  • PDF、Word、网页、Markdown
  • 内部 Wiki、工单、产品说明
  • 代码仓库中的文档与注释（视场景而定）

图中左侧的 Docs 即这一层输入。

3.2 Parsing + Preprocessing → Parsed docs

对原始文件做解析与清洗，常见动作包括：

  • 从 PDF / HTML 抽出正文
  • 去掉页眉页脚、导航、广告、乱码
  • 统一编码，保留标题、列表、表格等结构信息

输出是更干净、结构化的 Parsed docs，为后续切分和嵌入打基础。

3.3 Chunking → Chunks

把长文档切成较小的 chunks（块）。原因主要有三点：

原因 说明
模型长度限制 Embedding 与后续 Prompt 都有 token 上限
检索粒度 需要命中「相关段落」，而不是整本文件
噪声控制 整篇塞进上下文会稀释重点、浪费配额

常见切分策略：按固定字数 / token、按标题层级、滑动窗口并保留一定重叠。图中一摞 chunks 就是切分结果。

3.4 Embedding Model → Vectorize

每个 chunk 送入 Embedding Model（嵌入模型），把文本映射成高维向量（图中彩色条）。语义相近的文本，在向量空间中距离也更近。

关键约定：入库所用的嵌入模型，必须与在线查询时一致（或明确兼容）。换模型却不重建索引，检索质量会明显下降。

3.5 写入 Vector store

向量通常连同原文 chunk、来源路径、页码等元数据，一并写入 Vector store（向量库）。图中粉色数据库图标即此处。

至此 Indexing 完成：文档已从「不可直接检索的文件」变成「可按语义召回的知识库」。

4. Retrieve + Generate：在线问答

用户一提问，进入图下半部分的实时链路。

4.1 User → Query

用户提出自然语言问题，图中绿色圆 query。

4.2 对问题做 Embedding → Vectorize

使用与建库相同的 Embedding Model，把 query 也变成向量。这样问题和文档块处在同一向量空间，才能做有意义的相似度比较。

4.3 Retrieve：检索 Vector store

用问题向量在 Vector store 中做相似度搜索（常见为余弦相似度、点积，以及 ANN 近似最近邻），取出最相关的若干 chunk，得到图中的 Relevant docs。

工程上还可以叠加：

  • 元数据过滤（权限、时间、文件类型）
  • 重排序（Rerank）提升精排质量
  • Top-K、相似度阈值等召回控制

图中用箭头 Retrieve 概括「带着向量去库里取相关文档」这一步。

4.4 组装 Prompt

把下列内容拼成送给 LLM 的输入（图中黄色区域旁的 prompt）：

  • 用户原始 query
  • 检索到的 Relevant docs
  • 系统约束（例如：仅依据给定资料作答、资料不足时明确说明、尽量标注来源）

这就是「增强」：模型不再只依赖参数记忆，还带上了刚检索到的证据片段。

4.5 LLM → Generate → Response

LLM（图中蓝色六边形）根据增强后的 Prompt 执行 Generate，产出最终 response 返回用户。

理想行为是：答案主要依据 Relevant docs；资料不足时承认不确定，而不是补全虚构细节。

5. 两条线如何咬合

用流程把图中上下两部分串起来：

共享部件：

部件 作用
Embedding Model 文档块与问题共用同一套语义编码
Vector store Indexing 写入、Retrieve 读取的中枢

6. 与直接问 LLM 的对比

维度 直接问 LLM RAG
知识来源 训练数据 + 当前对话 训练知识 + 你索引过的文档
私有 / 最新资料 难以即时纳入 更新文档并重建或增量索引即可
可追溯性 弱 可引用具体 chunk / 文件来源
复杂度与成本 低 多了解析、切分、向量库与检索链路

RAG 不是取代 LLM，而是给生成过程装上「先查资料再回答」的外挂记忆。

7. 实践中的常见坑

对照流程图，落地时尤其要注意：

  1. Chunk 太大：检索不准，命中块里噪声多；太碎：上下文破碎，答案拼不起来。
  2. 换了 Embedding 却不重建库：查询向量与库内向量不在同一空间，召回失效。
  3. 只检索、不约束 Prompt：模型仍可能忽略资料自由发挥 → 系统提示里要明确「依据资料作答」。
  4. Indexing 质量差（解析乱、切分差、重复垃圾多）：后面 Retrieve / Generate 再优化也救不回来。
  5. 权限与数据范围：向量库若混入不该暴露的文档，检索可能把敏感片段送进 Prompt。

8. 小结

RAG 工作流程可以压成两句：

  1. Indexing：文档解析 → 分块 → 嵌入 → 存入向量库。
  2. Online：问题嵌入 → 检索相关块 → 与问题组成 Prompt → LLM 生成回答。

图中 Indexing 框解决的是「知识怎么进库」；下方 User → LLM 链路解决的是「提问时怎么把库用起来」。两者通过 Embedding Model 与 Vector store 对齐，才构成完整的检索增强生成。
