Agent Skills 的渐进式披露

Agent Skills 的渐进式披露

1. 是什么

渐进式披露（Progressive Disclosure）是 Agent Skills 的上下文加载策略：先只暴露技能的「名片」，真正用到某项技能时，再把完整说明读进上下文。

可以把它想成公司通讯录：

  • 平时只保留姓名、岗位、一句话职责；
  • 要找人办事时，再打开对方的完整档案（流程、脚本、注意事项）。

核心原则就六个字：用谁读谁，不用不读。

2. 为什么需要

Agent 的上下文窗口有限。如果启动时就把所有技能的 Markdown 正文一次性塞进去，会出现几类问题：

问题 表现
上下文膨胀 技能一多，有效对话空间被说明书占满
噪声干扰 无关技能的细节会干扰当前任务的规划
成本上升 Token 消耗增加，响应变慢、费用变高

渐进式披露把「能力目录」和「能力正文」拆开：目录始终可见、成本可控；正文按需加载、用完即可视为任务内的临时知识。

3. 三步怎么工作

3.1 启动时：只看「名片」

Agent 启动时，只会扫描各技能目录下的 SKILL.md，读取其中的 YAML 前置元数据（front matter），不会加载 Markdown 正文。

这份元数据相当于精简名片，通常包含：

  • name：技能名称
  • description：简短描述（一般限制在 1024 个字符内）

此时上下文里只有「有哪些技能、各自擅长什么」，没有具体操作步骤。Agent 据此做匹配判断，而不是背完整说明书。

3.2 运作时：按需调取详细档案

任务执行过程中，Agent 会把当前需求与已加载的技能描述对照：

  1. 描述与任务匹配 → 读取该技能 SKILL.md 的完整内容；
  2. 描述不匹配 → 继续保持未加载，不占上下文；
  3. 需要多项技能时 → 分别按需加载，而不是一次灌入全部技能正文。

这种「用谁读谁」的模式，就是渐进式披露的核心。

3.3 与 Memory 的区别

渐进式披露的 Skill，和始终驻留上下文的 Memory（如 AGENTS.md）不是同一类机制。

维度 Skill（渐进式披露） Memory（如 AGENTS.md）
加载时机 启动只读名片，命中后再读全文 会话中持续可用，全时驻留
上下文占用 平时极小，按需增长 相对固定，始终占位
用途定位 可插拔能力：流程、规范、脚本指引 长期偏好、项目约定、团队规则
扩展方式 技能变多，主要增加名片目录 内容变多，会持续挤压有效上下文

一句话区分：

  • Skill 是按需的、有渐进式披露的能力包；
  • Memory 是全时生效的背景知识。

把「偶尔才用的长流程」放进 Memory，会白白占上下文；把「每条对话都必须遵守的约束」只写成 Skill 而不进 Memory，又容易在未触发时被忽略。两者应分工，而不是互相替代。

4. Skill 与 Memory 对照

再压缩成选型视角：

你想放什么 更适合
发版检查清单、某类文档转换步骤、特定工具链操作 Skill
仓库命名规范、默认回复语言、禁止事项、团队协作约定 Memory
很长、很少触发、触发后才需要细节 Skill（靠渐进式披露）
短、几乎每次任务都相关 Memory

5. 写好技能描述的要点

渐进式披露能不能「找对人」，几乎完全取决于名片上的 description：

  1. 写清触发场景：用户会说哪些话、任务长什么样时该用这个技能。
  2. 写清能力边界：做什么、不做什么，避免和相邻技能抢匹配。
  3. 控制长度：描述通常有字符上限（如 1024），把细节留给正文。
  4. 正文承接细节：流程、命令、检查项、反例放进 Markdown 正文；只有命中后才会被读入。

名片负责被发现，正文负责被执行。渐进式披露把这两件事拆开，Agent 才能在技能数量增长时，仍然保持可控的上下文成本。
