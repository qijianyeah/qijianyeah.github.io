1. 什么是跨域

跨域，指浏览器里的页面去访问另一个「源」上的资源时，被同源策略拦截的现象。

源（Origin） 由三部分组成：

组成部分 例子
协议 http / https
域名（或主机名） 127.0.0.1、localhost、api.example.com
端口 3000、2024、443

只要这三项里有任意一项不同，浏览器就认为是两个不同的源，请求属于跨域。

页面地址 接口地址 是否跨域 原因
http://a.com/page http://a.com/api 否 协议、域名、端口都相同
http://a.com https://a.com 是 协议不同
http://a.com http://b.com 是 域名不同
http://127.0.0.1:3000 http://127.0.0.1:2024 是 端口不同
http://localhost:3000 http://127.0.0.1:3000 是 主机名不同（localhost ≠ 127.0.0.1）

最后一行很容易踩坑：在开发机上，localhost 和 127.0.0.1 往往指向同一台机器，但对浏览器来说它们仍然是两个不同的源。

2. 同源策略在保护什么

同源策略是浏览器的安全机制，不是 HTTP 协议本身的限制。

它要防止的典型风险是：

  1. 恶意网站用你的登录态，偷偷调用银行、邮箱等站点的接口。
  2. 恶意页面读取另一个站点返回的敏感数据。
  3. 在用户不知情的情况下，跨站点发起写操作。

因此：

  • 浏览器里的前端代码受同源策略约束。
  • curl、Postman、后端服务调后端不受这套规则约束。
  • 服务器常常已经正常处理了请求；真正“拦下来”的，经常是浏览器。

看到控制台里的 CORS 报错时，不要先怀疑“后端接口挂了”，而要先确认：是不是前端源没有被后端明确允许。

4. CORS 是怎么工作的

CORS（Cross-Origin Resource Sharing，跨域资源共享）是浏览器和服务器之间的一套约定：

  • 浏览器发起跨域请求时，会带上 Origin 请求头，告诉服务器“我是谁”。
  • 服务器如果同意，就在响应里带上 Access-Control-Allow-Origin 等响应头。
  • 浏览器看到允许信息后，才把响应交给前端 JavaScript。

4.1 简单请求

满足一定条件的 GET / POST 等请求，浏览器会直接发业务请求，然后根据响应头判断是否把结果交给页面。

4.2 预检请求（Preflight）

当请求可能修改数据，或使用了自定义头、非简单 Content-Type 时，浏览器往往会先发一个 OPTIONS 预检请求，询问服务器：

  • 允不允许这个源？
  • 允不允许这些方法？
  • 允不允许这些请求头？

服务器对 OPTIONS 做出肯定答复后，浏览器才会发出真正的 POST / PUT / DELETE 等业务请求。

4.3 和“代理”方案的区别

解决跨端访问还有另一种常见做法：开发时让前端同源代理到后端。

方案 思路 特点
CORS 后端明确允许前端源 前后端仍是两个源，靠响应头放行
开发代理 浏览器只访问前端同源地址，由前端开发服务器转发到后端 浏览器视角不再跨域

两种方案可以并存。CORS 解决的是“不同源之间能不能直接通信”；代理解决的是“让浏览器看起来像同源”。

5. 用 FastAPI 放开跨域

FastAPI 通过 CORSMiddleware 统一加 CORS 响应头，不必在每个接口里手写。

allow_methods 允许的方法；* 表示全部

前端如果改到了新端口，却没有同步改 allow_origins，就会再次出现跨域报错。

6. 常见报错与排查

6.1 控制台提示 blocked by CORS policy

优先检查：

  1. 浏览器地址栏里的前端源，是否一字不差地出现在 allow_origins 中。
  2. 有没有把 http://localhost:3000 写成了 http://127.0.0.1:3000，或反过来。
  3. 协议是否一致（http / https）。
  4. 后端服务是否真的在跑，中间件是否挂到了正确的 app 上。

6.2 预检 OPTIONS 失败

如果 Network 面板里先有一个红色的 OPTIONS：

  1. 确认后端没有把 OPTIONS 路由成 404。
  2. 确认 allow_methods、allow_headers 覆盖了实际请求用到的方法和头。
  3. 确认中间件加在路由注册之前或之后都能生效（Starlette/FastAPI 的中间件会包裹整个应用）。

6.3 带 Cookie 时仍然失败

同时核对这三点：

  1. 前端：credentials: "include"
  2. 后端：allow_credentials=True
  3. 后端：Access-Control-Allow-Origin 是具体源，不是 *

7. 生产环境要注意什么

开发阶段可以把本机常用源写进白名单；上线后不应继续沿用“本地端口随便放行”的配置。

建议：

  1. allow_origins 只保留真实前端域名，例如 https://app.example.com。
  2. 不要为了省事长期使用 allow_origins=["*"]，尤其是还要带 Cookie 的场景。
  3. 前后端如果最终部署到同域同端口（例如由 Nginx 反代到同一域名下），浏览器侧可能不再跨域，但内部服务之间的调用仍要按实际架构配置。
  4. 对管理后台、带登录态的接口，跨域白名单应尽量收紧，避免任意网站借用户浏览器发起带凭证请求。

一句话总结：

跨域不是接口“坏了”，而是浏览器要求：不同源之间通信，必须由目标服务器明确点头同意。CORS 就是这套“点头”协议；在 FastAPI 里，通常用 CORSMiddleware 一次性配好。
