1. 同一问题，两条路

任务复杂到一次提示词装不下时，Agent 仍然要把事情做完。Agent Skills 和 Multi-Agent 都在解决这件事，思路、实现路径和适用场景不一样。

  • Agent Skills 不增加决策者。同一个 Agent 配备一组可按需加载的技能，自己规划，自己调用。
  • Multi-Agent 增加决策者。任务被拆开，交给多个各自独立的 Agent，再由一个协调者把结果收回来。

一个是给同一个人加工具箱，一个是组一支团队。

2. 核心范式

2.1 Agent Skills：单体智能体，靠能力扩展

Agent Skills 是单体智能体（Single-Agent System，SAS）。系统里只有一个做规划的模型。能力变多，靠的是给这个模型挂技能。

技能是一份带触发条件的说明，后面可以跟脚本和参考资料。模型真正调用的函数仍然是工具：读文件、跑命令、查接口。技能告诉它什么时候用、按什么顺序用。

运行时，Agent 的上下文里先只有技能目录：name 和 description。任务和某条描述对上了，才把正文读进来。模型还是那一个，它会的步骤变多了。

2.2 Multi-Agent：多智能体，靠分解与协作

Multi-Agent 是多智能体系统（Multi-Agent System，MAS）。系统里有多个做规划的模型，各自拿独立上下文。

常见形态是一个 Supervisor 带若干子 Agent：

  • Supervisor 接收任务，识别意图，决定派给谁；需要时同时派给多个，再汇总。
  • 子 Agent 只承担一类工作，例如查调用链、改补丁、跑测试、做安全审查。
  • 成员之间不共享完整对话，只交接一份状态（State）。

3. 架构与工作流程

3.1 架构比喻

Agent Skills Multi-Agent
人怎么组织 一个专家，面前一个多功能工具箱，用哪件自己拿 一个项目经理带一支专业团队，成员各司其职
新增一种能力时 往工具箱里加一份技能说明 增加一个角色，并约定它和经理之间的交接

3.2 单一 Agent 怎么把技能用起来

  1. 用户把任务交给唯一的 Agent。
  2. Agent 对照已加载的技能描述，决定用不用技能、用哪几个。
  3. 命中后加载对应技能的详细说明，仍在同一段上下文里继续规划。
  4. 按技能里的步骤调用工具，看结果，直到任务结束。

下一步由同一个模型在当前会话里决定。选技能就是把说明读进这份上下文。

3.3 Supervisor 怎么把任务派出去

  1. Supervisor 接收任务，识别意图。
  2. 写成一份交接状态：目标、约束、已有产物、希望子 Agent 返回什么。
  3. 把状态分给一个或多个子 Agent。每个子 Agent 单独调用一次模型。
  4. Supervisor 收回结果，决定结束、再派一轮，或交给另一个子 Agent。

这就是团队之间的工单。子 Agent 看不到 Supervisor 的全部历史，也看不到其他子 Agent 的上下文，只看这份状态里写明的内容。

4. 上下文管理

4.1 渐进式披露，上下文共享

Agent Skills 默认不把所有技能正文塞进提示词。上下文里先放目录，用到某一个技能时再加载它的说明、参考文档或脚本。

技能共享同一个上下文。前面步骤的结论，后面的技能直接看得到，不用再写交接。

目录变长之后，光是「有哪些技能」就会占掉窗口，并干扰模型对当前任务的注意力。技能数量过多时，选错技能、漏掉约束会明显变多，性能下降往往是突然的。这是单体上下文的物理上限，一般称为认知过载：说明写得再清楚，窗口长度和注意力都有限。

缓解办法是收目录，把正文留到真正命中时再加载：

  • 描述写成「什么时候用」，不要写成技能正文的摘要。
  • 相近技能合并，或按领域分成少量入口，入口里面再指向详细说明。
  • 稳定、互不相关、又必须隔离权限的角色，再考虑拆成独立 Agent。

4.2 上下文隔离，用状态传递关键信息

Multi-Agent 把上下文切开。每个子 Agent 有自己的系统提示、工具权限和对话记录。它们之间只传递关键信息：目标、约束、文件路径、上一步结论。

隔离能做三件共享上下文做不到的事：

  • 不同子 Agent 使用不同模型。
  • 并行拿出互不污染的意见，例如一个写方案，一个专门挑错。
  • 按 Agent 切开隐私和权限。看过密钥的 Agent 只在状态里留下「已核验」，原文不进入负责写文档的 Agent。

状态里没写的约束，子 Agent 不会知道。交接要有固定字段，把整段聊天记录贴过去就失去了隔离，也把 Token 成本加回来了。

5. 通信成本

Agent Skills Multi-Agent
模型调用 同一个 Agent 的循环。工具返回后，仍由它看结果并决定下一步 每个子 Agent 的每次执行，都是一次独立的模型调用
额外开销 工具自己的 I/O：读文件、跑命令、请求接口 每次调用都重传系统提示、交接状态和子任务，再加一份输出
延迟与费用 低，没有 Agent 之间的模型往返 高，Token 按调用次数累加；串行派发时墙钟时间近似等于各跳之和

Agent Skills 的循环里可以有多次模型补全。这些补全共享同一份上下文，中间没有第二个模型接手。

Multi-Agent 并行派发可以缩短墙钟时间，费用仍按次数相加。子 Agent 理解偏了，Supervisor 再派一轮，输入和输出都要再付一次。

6. 优势、劣势与选型

6.1 Agent Skills

适合步骤有先后、中间结果要留给下一步的任务：按清单做代码审查、按规范改一个模块、把一份资料整理成文章。路径短，提示词好维护，延迟低。

技能一多，目录本身变成负担，路由质量会掉。技能之间没有权限边界，也没有「换一个模型独立给意见」的位置。

6.2 Multi-Agent

适合角色已经分得开的协作：不同专业、不同模型、并行意见、隐私或工具权限必须隔离。某个子 Agent 失败时可以重试或替换，不必推翻整段上下文，容错更好。

角色、交接协议和失败策略都要单独设计。运行时要处理反复派发、结论互相矛盾、状态过时。架构、通信、协调的开销，以及开发和运维成本，都高于技能模式。

6.3 怎么选

任务特征 更合适的做法
前后步骤强依赖，延迟敏感，一个模型就能做完 Agent Skills
角色分工明确，要并行，或要隔离权限和模型 Multi-Agent
技能已经多到经常选错 先合并、分组技能；目录仍然压不住，再把稳定角色拆成子 Agent
协作很重，但每个角色内部的步骤是固定的 Supervisor 负责分活，子 Agent 内部再用 Skills

能用一个 Agent 加几个技能做完的事，拆成多次独立模型调用后，多出来的是 Token 和协调成本。

7. Agent Skills 与 Multi-Agent 对照总表

对比维度 Agent Skills（技能模式） Multi-Agent 架构
核心范式 单体智能体（SAS），通过能力扩展 多智能体系统（MAS），通过任务分解与协作
架构比喻 一个专家配备一个多功能工具箱，工具按需取用 一个项目经理带领一个专业团队，成员各司其职
工作流程 单一 Agent 根据任务自主规划，并调用一个或多个技能 Supervisor 接收任务，识别意图，分配给特定子 Agent 执行，并可协调多个子 Agent
上下文管理 渐进式披露：仅预加载技能描述，需要时再加载技能详情，上下文共享 上下文隔离：每个子 Agent 拥有独立的上下文，通过状态（State）在 Agent 间传递关键信息
通信成本 低。同一个 Agent 的多次补全共享上下文，选技能不产生 Agent 之间的模型往返 高。每次子 Agent 的调用都是一次独立的模型调用，产生额外的 Token 消耗和延迟
优势 高效、简洁、低延迟。适合逻辑线性、可序列化的任务 专业化、容错性高、适合复杂协作。能处理不同模型、并行意见或隐私隔离的任务
劣势 存在认知过载的物理极限，技能数量过多时性能会急剧下降 架构复杂，通信和协调开销大，开发和运维成本高

8. 扩展说明

8.1 Supervisor 是什么

Supervisor 是 Multi-Agent 里负责分活和收口的那个 Agent，相当于项目经理。具体业务由子 Agent 做。

它做四件事：

  1. 接任务。用户的请求先到它这里。
  2. 识别意图。判断这是查代码、改补丁、跑测试，还是要好几件事一起做。
  3. 派发。写成一份状态交给对应的子 Agent：目标、约束、已有材料和希望返回的结果。需要时可以同时派给多个。
  4. 协调。收回各子 Agent 的结果，决定结束、再派一轮，或交给下一个子 Agent。

子 Agent 看不到 Supervisor 的完整对话，只看这份状态。Supervisor 自己通常不深入每个专业步骤，它的上下文里主要是任务和各子 Agent 交回来的结论。
