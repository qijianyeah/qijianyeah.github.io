MCP 与 HTTP 的本质区别：谁做决策，就为谁提供语义

MCP 与 HTTP 的本质区别：谁做决策，就为谁提供语义

1. 三个被反复问起的问题

在做 AI Agent 接入内部服务时，下面三个问题几乎必然出现：

  1. MCP 和 HTTP 到底差在哪？是不是 MCP 更”高级”？
  2. 我有个 Java 服务，只提供 HTTP 接口，必须再写一个 MCP 服务当中间层吗？
  3. 我用 requests 调了接口，这算不算 Agent 自动调用？必须包成 MCP 才算吗？

这三个问题的答案其实都指向同一个判据：谁是这次调用的决策者。想清楚这一点，选型就没有模糊地带。

2. HTTP 与 MCP 的定位差异

2.1 HTTP：一条只负责搬运的传送带

HTTP 是超文本传输协议，它解决的是”字节如何从 A 点可靠地到达 B 点”：方法、路径、请求头、状态码、报文体。它不携带任何业务语义——POST /api/orders 这串字符对人类工程师有意义，是因为有人读了文档、写了代码；对模型来说它只是一串没有解释的路径。

HTTP 的另一个特点是：它自己就是最底层的通用管道，不依赖别的应用层协议来描述自己。

2.2 MCP：一本带图解的送货手册

MCP（Model Context Protocol）是让大语言模型在运行时动态发现并理解外部工具语义的标准化握手规范。它基于 JSON-RPC 2.0，把一次工具接入拆成三个角色：

角色 职责
Host 宿主程序，通常是 AI 应用本身，负责编排模型与 MCP 客户端
Client MCP 客户端，与 Server 建立一对一连接
Server 能力提供方，暴露 tools / resources / prompts 三类能力

2.3 一张表看清差别

维度 HTTP MCP
本质 传输协议，负责搬运字节 工具供给与语义描述规范，负责描述能力
提供了什么信息 方法、路径、状态码、报文体 工具名、自然语言描述、参数 JSON Schema、返回结构
谁来理解它 人类工程师、确定性代码 LLM 宿主程序 + LLM
是否描述业务含义 不描述 描述，且描述质量直接决定调用准确率
与底层的关系 本身就是底层管道 运行在 HTTP / stdio 等传输之上
选错的表现 模型看不懂接口，参数乱填 确定性脚本多绕一层，增加延迟与维护面

一句话概括这层差异：HTTP 运数据，MCP 运理解。

3. 唯一判据：调用主体是谁

如果上面的图看着别扭，用文字描述同样清晰：

分支 条件 结论
① 调用主体是人类写好的固定脚本 直接用 HTTP / requests，不需要 MCP
② 调用主体是 LLM 动态决策，且服务已有 MCP 语义描述 直接连接 MCP Server
③ 调用主体是 LLM 动态决策，但服务只有 HTTP 接口 先写 MCP 适配器，再连接 MCP Server

判据不是”新与旧”，也不是”谁更强”，而是调用主体的认知模式：确定性程序靠契约驱动，智能体靠语义驱动。

4. 场景一：调用 Java 服务要不要写 MCP 适配器

4.1 结论

  • 调用主体是确定性代码：不需要。Java 服务暴露 HTTP，你用 RestTemplate、WebClient、Feign 直接调，这是最稳的方案。
  • 调用主体是LLM，且目标 Java 服务只提供 HTTP 接口、没有原生 MCP 能力：必须补一个语义翻译层，否则模型看不见这个服务的存在，也无从判断该不该调、怎么填参数。

4.2 适配器到底在做什么

适配器不是”再包装一层 HTTP”，它做的是把机器看不懂的接口契约，翻译成模型能读懂的工具描述。核心是三件事：

步骤 输入 输出
发现 OpenAPI 文档、Controller 方法签名 工具清单
描述 参数类型、必填项、取值枚举、业务含义 工具名 + 自然语言描述 + 参数 JSON Schema
转发 模型填好的参数 真实的 HTTP 请求，以及结构化的返回结果

一个 OpenAPI 元素到 MCP tool 的映射大致如下：

OpenAPI MCP tool
operationId tool name
summary / description tool description（进入模型上下文的关键字段）
parameters / requestBody tool inputSchema（JSON Schema）
enum、required、format 参数约束，收敛模型自由度
responses 返回结构说明，供模型解读结果

4.4 适配器什么时候可以拆掉

当目标服务原生支持 MCP 时，手工适配层自然失去意义。但要注意”能拆”和”该拆”是两件事：如果适配层里沉淀了鉴权透传、限流、字段脱敏、错误语义归一这些逻辑，它们不会因为服务支持了 MCP 就消失，只是换了个位置存在。

5. 场景二：用 requests 发的请求算不算 Agent 自动调用

5.1 硬编码与运行时决策的分界

这段脚本永远不会被算作 Agent 自动调用。它本质上是”提前录好的一段语音指令，让机器人按时播放”，机器人只是在复读，没有任何理解与判断。

对比项 硬编码脚本 Agent 自动调用
目标由谁定 开发者在编码阶段定死 模型在运行时根据用户意图选择
参数由谁填 代码里写死，或从固定变量拼装 模型根据上下文生成
时机由谁定 cron、事件、手工触发 模型在对话流程中自主判断
出错后谁补救 开发者改代码 模型读取错误信息后重新决策
模型是否感知该服务 完全不感知 通过语义描述感知

5.2 想让它变成”模型能用的工具”，需要补语义层

语义层的形式可以是 MCP 工具，也可以是 LangChain Tool、OpenAI Function Calling 等任意一种工具描述抽象。它们解决的问题是同一个：**把”一段固定的 HTTP 调用”升格为”一个带说明书的可决策动作”**。

5.3 封装质量决定决策质量

同一个接口，描述写得潦草和写得讲究，模型的调用准确率天差地别。验收时可以逐条对照：

检查项 不合格 合格
工具名 api_call_1 close_order
描述 “调用关闭订单接口” 说明适用场景、不适用场景、副作用
参数约束 全部是宽泛的 str 明确的枚举、格式、必填标记
返回结构 直接吐 HTML 或超长 JSON 裁剪后的稳定字段
错误信息 500 Internal Server Error “订单已发货，无法关闭”

工具描述越收敛，模型发挥的自由空间越小，行为越稳定。你不给 AI 确定性，AI 就不给你确定性。

6. 六个高频消歧点

一、MCP 不是 HTTP 的升级替代品。 二者不在同一层。MCP 不负责数据传输，它只是在 HTTP（或 stdio）之上叠加了一层机器可读的语义契约。MCP 的传输层本身就可以跑在 HTTP 上，说”MCP 取代 HTTP”等于说”说明书取代了纸”。

二、MCP 不等于 tool call。 这是最容易混淆的一组概念：

概念 所处位置 作用
MCP 工具描述 Server 侧 告诉模型”有哪些能力可用”
tool call 模型侧 模型产出的”我要调某个工具、参数是这些”的意图
工具执行 宿主 / 框架侧 真正发起请求、拿到结果、回填给模型

三、执行不是大模型干的活。 模型只输出决策意图，实际的 HTTP 请求、重试、超时控制、结果回填，全部由宿主框架完成。把模型当成”工具脑”，把框架当成”手脚”，分工才不会错。

四、MCP 不是智能体的必需品。 只要具备”工具名 + 描述 + 参数 Schema”这三个要素，LangChain Tool、Function Calling、以及各家 Agent 框架都能达成同样的效果。MCP 的价值在于标准化：一次编写，多个宿主复用，不必为每个框架重写一遍适配代码。

五、加了 MCP 不等于变聪明。 语义层只是把服务暴露给模型，暴露得好不好，取决于描述写得好不好。把 OpenAPI 的 operationId 机械地塞进工具名、把接口注释直接当 description，往往得到一堆模型看不懂的工具。

六、语义层的代价要算清楚。 多一层就多一次序列化、一次网络跳转、一份可能漂移的契约。对延迟敏感的链路、超高并发的内部调用、结构稳定的批处理任务，让确定性代码直连 HTTP 才是正确选择。

7. 选型速查表

场景 调用主体 目标服务形态 推荐方案
定时数据同步、ETL 确定性脚本 HTTP 直接 HTTP / requests
内部高频 RPC 确定性服务 HTTP / gRPC 直接调用，不加语义层
让 AI 助手查询工单状态 LLM 只有 HTTP 接口 写 MCP 适配器包装接口
接第三方已有的 MCP Server LLM MCP MCP Client 直连
单体 Java 服务内让模型调用本地方法 LLM Spring Bean Spring AI @Tool / MCP Server Starter
多框架复用的工具库 LLM 任意 统一封装为 MCP Server

8. 总结

把整件事压缩成四句话：

  • HTTP 只提供运输能力，不提供语义描述，模型无法从路径和状态码中读出业务意图。
  • 想让一个 HTTP 接口成为模型可理解、可决策的工具，就要把它封装成带语义的工具描述（MCP 工具或等价抽象）。
  • 执行由框架完成，决策由模型完成；给模型语义，给框架确定性。
  • 选型的判断标准是调用主体的认知模式：确定性程序用契约驱动，智能体用语义驱动。

HTTP 运数据，MCP 运理解；谁做决策，就为谁匹配对应的语义供给方式。
