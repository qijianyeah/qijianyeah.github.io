前端发起 GET/POST 时后端发生了什么：从报文解析到自定义请求头

发表于2026-09-02|更新于2026-09-02|Java Web
|浏览量:

前端无论发 GET 还是 POST，后端走的都是同一条处理管道。真正的差别在报文怎么带参数，以及 Spring 怎么把这些参数绑到方法上。请求头对两种方法一视同仁：都在报文最前面，Tomcat 解析完就能用，不走 Jackson。

本文以 Spring Boot + 嵌入式 Tomcat 为例，从请求进机讲到响应出机，并补上请求头的读取、框架消费，以及自定义头的前后端约定。

1. 先看报文：GET 和 POST 差在哪

浏览器或 axios 发出去的，本质都是一段 HTTP 报文。

GET 查用户：

参数在 URL 路径或查询字符串里，没有 Body。

POST 新建用户：

参数在 Body 里，方法名告诉服务器这是一次提交或变更。

对比项 GET POST
语义 获取资源 提交 / 创建资源
参数位置 URL（path / query） Body
幂等 是（多次调用结果应一样） 通常否
缓存 可被浏览器 / CDN 缓存 一般不缓存
长度 受 URL 长度限制 主要受 Body 与服务器限制

后端不会因为「是 POST」就自动写库，也不会因为「是 GET」就自动只读。写不写库，完全取决于映射到的那个方法里写了什么。

2. 报文进 JVM 之前：Tomcat 如何读请求

  1. DNS 解析、TCP 三次握手；HTTPS 再加一层 TLS。
  2. 操作系统把数据包交给监听端口的进程（嵌入式 Tomcat 默认 8080）。
  3. Tomcat 的 Acceptor 接受连接，从线程池取出 Worker 读 socket。
  4. Http11Processor 解析出：方法（GET / POST）、URI、Header、QueryString。若是 POST，再按 Content-Length 或 chunked 把 Body 读进 HttpServletRequest。

到这一步，GET 和 POST 已经分叉：GET 通常没有 Body；POST 必须把 Body 读完（或交给后续流式读取），否则 Controller 拿不到 JSON。

Header 比 Body 更早可用。鉴权、限流、租户识别都应该在 Filter / Interceptor 里读头，不要等进 Controller 再判断。

3. Filter 到 DispatcherServlet：统一分发

Tomcat 把请求包装成 HttpServletRequest / HttpServletResponse，丢进 FilterChain：

Filter 不关心业务，只做横切：鉴权失败这里直接 401 / 403 返回，根本进不了 Controller。

Spring Security 对 GET / POST 还有一点差异：默认 CSRF 保护对 状态变更方法（POST / PUT / DELETE）更严；纯 REST + JWT 通常会关掉 Session CSRF，改用 Token。

3.1 DispatcherServlet 怎么找到方法

Spring MVC 所有请求都先进 DispatcherServlet（前端控制器）：

  1. HandlerMapping 用「HTTP 方法 + URL」找处理器。例如 @GetMapping("/api/users/{id}") 只匹配 GET；POST 打到同一个 URL 会 405 Method Not Allowed。
  2. 得到 HandlerExecutionChain = Controller 方法 + Interceptor 链。
  3. preHandle：登录校验、日志、限流。返回 false 则短路。
  4. HandlerAdapter（一般是 RequestMappingHandlerAdapter）真正调用 Controller 方法。
  5. postHandle / afterCompletion：收尾、记耗时、清 ThreadLocal。

匹配规则是 方法 + 路径一起看，不是只看 URL。这就是「前端发错方法，后端 405」的原因。

4. 参数绑定：GET 和 POST 在这里分家

适配器调用方法前，要把 HTTP 数据绑到 Java 参数上。

GET：

  • @PathVariable ← URI 里的 {id}
  • @RequestParam ← ?status=active
  • 没有 Body，不会走 JSON 反序列化

POST：

  • @RequestBody 触发 HttpMessageConverter（Jackson）
  • 按 Content-Type: application/json 把字节流反序列化成对象
  • @Valid 触发 Bean Validation；失败直接 400，进不了 Service

表单 POST（application/x-www-form-urlencoded）则更像 GET：用 @RequestParam / 对象绑定，不走 JSON Converter。

取值来源 GET JSON POST 表单 POST
Path / Query @PathVariable / @RequestParam 仍可用 仍可用
Body 通常无 @RequestBody + Jackson @RequestParam / 表单对象
失败表现 缺必填参数 400 JSON 非法 / 校验失败 400；类型不支持 415 缺字段 400

所以后端「发生了什么」的关键差异是：

  • GET：从 URI / Query 取值，便宜、可缓存、有长度限制
  • POST：从 Body 取值，要读流、反序列化、校验，通常不能被 CDN 当只读缓存

5. 业务层与响应写回

进了 Controller 之后，分层一般是：

  • GET：查缓存 / 查库，组 VO，通常不加写事务
  • POST：开事务、插库、发消息、清缓存；失败回滚

事务、锁、幂等，是业务代码决定的，不是 HTTP 方法自动带的。实务上 POST 创建接口常常还要自己做幂等（唯一键、幂等键），因为网络重试会把同一个 POST 打两次。

5.1 响应怎么回去

  1. Controller 返回对象（或 ResponseEntity）。
  2. @RestController 走 HttpMessageConverter，对象 → JSON 字节。
  3. 写入 HttpServletResponse：状态码、Header、Body。
  4. Filter / Interceptor 的 afterCompletion 执行。
  5. Tomcat 把字节写回 socket，连接 keep-alive 或四次挥手。

常见状态码：

场景 状态码
GET 成功 200，Body 是资源
POST 创建成功 更规范是 201 Created + Location，很多项目仍返回 200
URL 不存在 404
方法不匹配 405
Body 解析 / 校验失败 400
Content-Type 不支持 415
Accept 无法满足 406
未登录 / 没权限 401 / 403

7. 后端如何处理请求头

业务代码「读取」和框架「消费」是两回事。很多头你没写 @RequestHeader，框架已经用过了。

7.1 框架自动消费的头

请求头 谁处理 做什么
Content-Type HttpMessageConverter / Servlet 决定 Body 怎么反序列化
Content-Length / Transfer-Encoding Tomcat 决定 Body 读多长；异常或过大 → 400 / 413
Accept 内容协商 决定响应是 JSON 还是 XML
Accept-Language LocaleResolver 国际化
Cookie Servlet / Spring Session 解析 JSESSIONID 等，恢复 Session
Authorization Spring Security Bearer Token、Basic Auth
Origin / Access-Control-Request-* CORS Filter 跨域预检
If-None-Match / If-Modified-Since 静态资源 / 缓存过滤器 可能直接 304
X-Forwarded-For / X-Forwarded-Proto ForwardedHeaderFilter 还原真实 IP、HTTPS（经网关时）

7.2 鉴权头：Spring Security 的典型路径

自定义头做鉴权也可以，但要自己写 Filter，并在 Security 链里登记。不要只在 Controller 里校验，否则未保护的路径会漏。

7.3 跨域头：浏览器会先发 OPTIONS

当前端域名和 API 域名不同，且带了自定义头或 Authorization 时，浏览器先发 预检：

后端 CORS 配置必须 允许这些头，否则浏览器直接拦截，请求根本不会变成真正的 POST。

配置项 作用
allowedHeaders 浏览器 允许发送 哪些请求头
exposedHeaders 前端 JS 允许读取 哪些响应头（自定义响应头默认读不到）
allowCredentials(true) 允许带 Cookie；此时 不能 allowedOrigins("*")

7.4 网关 / 反向代理会改头

生产里请求常经 Nginx / Gateway，这些头会被改或追加：

  • 追加 X-Forwarded-For、X-Real-IP
  • 丢掉过长或未知头（Nginx underscores_in_headers：带下划线的头默认可能被丢）
  • 网关鉴权后注入 X-User-Id

后端若要用客户端 IP，应读转发头，并只信任自己网关，防止伪造 X-Forwarded-For。

7.5 处理时的常见坑

  1. 头会被日志打出来：Authorization、Cookie、自定义 Token 不要明文打 INFO 日志。
  2. 头有长度限制：Tomcat 默认 Header 总大小约 8KB（maxHttpHeaderSize），Cookie 过多会 400。
  3. 不要用头传大 JSON：头不是 Body，CDN / 代理可能截断。
  4. 编码：非 ASCII 值要用 RFC 5987；中文放头里容易乱码，能放 Body 就放 Body。

8. 前后端如何使用自定义请求头

约定一个名字，前端带上，后端读。常见用途：链路追踪、租户、灰度、防重放。

8.1 命名

现在不必强行 X- 前缀（RFC 6648 已不鼓励），但业界仍大量使用。建议：

  • X-Request-Id / X-Trace-Id：链路追踪
  • X-Tenant-Id：多租户
  • X-Idempotency-Key：POST 幂等
  • 不要发明 X_User_Id（下划线，Nginx 可能丢）
  • 不要把密码放自定义头

浏览器禁止前端改 Host、Content-Length、Origin 等标准头。自定义头没有这个限制，所以追踪 ID、租户 ID 才用自定义头。

8.4 一套可落地的约定

GET 和 POST 都能带自定义头。差别只在业务语义：GET 适合带租户、追踪；幂等键、提交令牌这类「这次写操作的身份」只放在 POST / PUT 上。

9. 整条链路串起来

阶段 GET POST
读 Header 相同 相同
读 Body 通常无 按 Content-Type 读并反序列化
匹配处理器 @GetMapping @PostMapping
业务语义 读资源，宜幂等 写资源，宜自备幂等键
自定义头 追踪、租户 追踪、租户、幂等键

10. 小结

  • GET / POST 在协议和参数绑定上不同，进 Service 之后是同一套分层。后端真正「知道」这是读还是写，靠的是 @GetMapping / @PostMapping 以及方法里的业务代码。
  • 取头用 @RequestHeader 或 request.getHeader()；Filter / Interceptor 里只能用后者。
  • 处理头分「框架自动消费」（Content-Type、Authorization、Accept、CORS）和「业务自己读」。
  • 自定义头要前端带、后端读、CORS 放行（allowedHeaders + exposedHeaders），必要时再回写到响应。
  • Header 比 Body 更早可用，鉴权与追踪应放在 Filter / Interceptor，不要等进 Controller。
