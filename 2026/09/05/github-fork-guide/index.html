GitHub Fork 完全指南：从复制仓库到同步与提 PR

发表于2026-09-05|更新于2026-09-05|工具与实践
|浏览量:

没有写权限的开源仓库，不能直接往别人的 main 上推代码。GitHub 的做法是：先 Fork 一份到自己名下，在自己的副本上改，再发 Pull Request（PR，拉取请求） 请上游审查并合并。日常贡献开源、练习项目、给公司仓库提补丁，走的都是这条路。

本文按 GitHub 当前网页、CLI 和命令行三种入口，把 Fork 从「点一下」讲到「长期维护」。

1. Fork 是什么

Fork 是把别人的仓库复制成你账号（或你有权限的组织）下的一个独立仓库。这份副本叫 fork，原来的仓库叫 upstream（上游）。

Fork 不是「再点一次 Clone」。它会在 GitHub 上真正新建一个仓库：有自己的设置、协作者、Issues、Pull Request、Actions、Projects。网页上打开 fork 时，仓库名下方会标明它从哪个上游复制而来。

典型用途有三种：

  1. 给开源项目提补丁：你没有上游写权限，只能改自己的 fork，再用 PR 申请合并。
  2. 基于别人的项目做自己的版本：先 fork 一份当起点，再按自己的方向改。
  3. 练习 GitHub 协作：官方练习仓库是 octocat/Spoon-Knife，专门用来练 fork、clone、同步。

2. Fork、Clone、Branch 差在哪

这三件事最容易混。

操作 发生在哪 结果 典型下一步
Fork GitHub 服务器上 你名下多出一个独立仓库，仍连着上游 Clone 到本地，或直接在网页改
Clone 你的电脑上 把某个远程仓库下载成本地目录 git add / commit / push
Branch 同一个仓库内部 多一条平行历史，不新建仓库 在分支上开发，再开 PR

要点：

  • Branch 是同一个仓库里的分岔；Fork 是另一个仓库。
  • 你可以直接 clone 上游，但没有写权限时 git push 会失败。Fork 之后，origin 指向你自己的仓库，推送就通了。
  • 只想本地看看代码、不打算回馈上游，clone 上游即可，不必 fork。
  • 打算提 PR，就应该 fork，而不是只 clone 上游。

3. 哪些仓库可以 Fork

公开仓库可以 fork 到：

  • 你的个人账号
  • 你有「创建仓库」权限的组织

私有仓库要同时满足：你已经有访问权限，并且仓库主人允许 fork。然后可以 fork 到个人账号，或 GitHub Team 计划下有创建权限的组织。用 GitHub Free 的组织不能接收私有仓库的 fork。

仓库、组织、企业策略都可以限制「能不能 fork、能 fork 到哪里」。企业托管用户（Enterprise Managed Users）还有额外限制。

可见性跟着上游走：公开仓库的 fork 是公开的，私有仓库的 fork 是私有的。不能单独把某个 fork 改成另一种可见性。 上游、所有 fork、以及 fork 的 fork，构成同一个「仓库网络」，共享同一套可见性。

8. 在 Fork 上改代码

不要直接在 main 上改。给上游提 PR 时，应在 fork 里开一条功能分支。

改文件后：

-u origin 把这条本地分支跟踪到你的 fork。以后在这条分支上再 git push 即可。

原则：

  • 一个 PR 对应一条分支，主题单一，review 更轻松。
  • 不要把一堆无关改动塞进同一条分支。
  • 推送目标必须是 origin，不是 upstream。

9. Fork 提交 vs 自己项目提交

git add 和 git commit 两条命令完全一样。真正不一样的是：远程指向谁、推到哪条分支、推完算不算完事。

自己的项目：origin 就是最终仓库，推上去工作就落地了。
Fork 贡献：origin 只是你的副本，推上去只是「改动到了自己的 GitHub」，还要再开 PR 才会进上游。

10. 从 Fork 给上游提 PR

PR 是 Pull Request 的缩写，中文常叫「拉取请求」或「合并请求」。意思是：请对方把你分支上的提交 pull（拉） 进他们的仓库。

你没有上游写权限，不能 git push 到别人的 main。正确流程是把改动推到自己的 fork，然后开一个 PR，对上游说：「请审查这批改动，同意就合并。」维护者可以在 PR 页面看 diff、留言、跑检查，通过后再点 Merge。GitLab 上同类功能叫 Merge Request（MR），本质一样。

代码已经在你的 fork 的某条分支上之后，就可以开这个 PR。

10.1 网页上最常见的路径

推送分支后，打开上游仓库，顶部常会出现黄色横幅 Compare & pull request，点它即可。

横幅没出现时：

  1. 打开上游仓库。
  2. 点 Pull requests → New pull request。
  3. 点 compare across forks（跨 fork 比较）。
  4. base repository / base branch：上游，以及你希望合入的分支（一般是 main）。
  5. head repository / compare branch：你的 fork，以及刚才推送的功能分支。
  6. 填写标题和说明。说明里写清改了什么、为什么、怎么验证。
  7. 个人账号下的 fork，可勾选 Allow edits from maintainers（允许维护者改你的 PR 分支）。组织拥有的 fork 不能把推送权交给维护者。
  8. 点 Create Pull Request。也可以先建 Draft PR，改完再标 ready。

方向不要反：左边是上游要接收的分支（base），右边是你 fork 上的改动（compare）。

11. 同步 Fork：跟上上游

上游合并了别人的 PR，你的 fork 就会落后。落后太久再提 PR，冲突会很难解。同步有三种做法。

11.1 网页：Sync fork

  1. 打开你的 fork 主页。
  2. 文件列表上方找到 Sync fork。
  3. 看清上游多了哪些提交，点 Update branch。

若同步会造成冲突，GitHub 会让你改走「开一个 PR 来解决冲突」。

11.3 命令行：fetch + merge

先确保已经加了 upstream（第 7 节）。

git fetch upstream 只下载，不改你当前分支。上游的 main 会出现在本地的 upstream/main。

  • 本地 main 没有独有提交时，合并一般是 fast-forward，最干净。
  • 本地 main 已经有自己的提交时，可能产生冲突，按普通合并冲突处理后再 push。

12. 允许维护者改你的 PR 分支

从个人 fork 提 PR 时，建议勾选 Allow edits from maintainers。维护者可以直接往你的 PR 分支推小修复，而不必只在评论里告诉你「再改一行」。

勾选后他们能做的事：补测试、改冲突、跑 CI 需要的微调。

如果 fork 里有 GitHub Actions 工作流，选项会变成 Allow edits and access to secrets by maintainers。这会让维护者有机会编辑 fork 里的 workflow，从而碰到 secrets、甚至影响到其他分支。仓库里有 workflow 和 secrets 时，先读清提示再勾。

组织拥有的 fork，不能把这种推送权交给上游维护者。

这一项管的是写 PR 分支，不是「上游能不能读你的代码」。读和写的完整边界见下一节。

13. 上游能随意拉取 fork 里的代码吗

不能随便改你的 fork，但读代码的权限比很多人以为的宽。GitHub 把「拉代码」和「往 fork 里写」分成两套规则。

13.1 先分清读和写

动作 公开 fork 私有 fork
读 / clone / fetch 你推上去的提交 能。fork 是公开的，谁都能拉；上游还有网络级可见性 上游有权限的人通常也能读；团队权限还会继承到私有 fork
往你的 fork 里 push 默认不能 上游团队若对原仓库有写权限，私有 fork 会继承，有可能也能写
改你正在提的 PR 分支 只有勾了 Allow edits from maintainers 才行 组织名下的 fork 不能把这种推送权交给维护者

结论：upstream 不能把你的 fork 当自己的仓库随便改；但「拉走你已经 push 上去的代码」基本做得到。

13.2 公开仓库：拉代码几乎没有门槛

公开 fork 本身就是公开仓库。上游维护者、路人，都可以：

这不依赖 PR，也不需要你额外授权。你一 git push origin，代码就已经在 GitHub 上公开了。

GitHub 还多了一层 fork 网络（repository network）：上游、所有 fork、fork 的 fork，共享同一套 Git 对象。官方说明包括：

  • 推到网络里任一仓库的 commit，其他仓库（包括上游）仍可能读到
  • 上游仓库的 owner 可以阅读该网络里的所有 fork
  • 即使后来删了 fork，贡献过的代码仍可能留在网络里

实操上常见的是：只要知道 commit SHA，就能在上游仓库 URL 下打开那个提交，哪怕这个提交只存在于某个人的 fork、从未合进 main。

开 PR 只是把「请审查并合并」说清楚，并给上游一条稳定的取代码入口（例如 pull/123/head）。不开 PR，公开 fork 上的代码照样能被拉走。

13.3 「允许维护者编辑」管的是写，不是读

勾选 Allow edits from maintainers（第 12 节）之后，有上游写权限的人可以往 这条 PR 的 compare 分支 推提交，方便他们补测试、改冲突。

这不是「随意拉取」的开关：

  • 没勾：他们仍然能读、能 fetch PR 分支，只是不能 push 回你的 fork
  • 勾了：多出来的是 写那一条分支，不是整个 fork 的所有分支
  • fork 里若有 GitHub Actions，选项会变成 Allow edits and access to secrets by maintainers，风险更大，要单独评估

13.4 私有仓库更严，也更反直觉

私有 fork 会 继承上游的权限结构。上游某个团队对原仓库有读/写，通常对私有 fork 也有同样权限。这时上游侧有权限的人，不只是能拉，写权限也可能跟着过来。

私有上游被删、或某人失去访问权时，对应的私有 fork 往往会被一并删掉。本地 clone 还在，但 GitHub 上的副本没了。

13.5 和日常口诀怎么对上

  • 你 push 到 origin 的代码，默认就默认可被上游看到（公开 fork 尤其如此）
  • 上游不能因此获得你整个 fork 的写权限（除非私有 fork 继承了写权限，或你勾了维护者编辑）
  • 不想再和上游共享 Git 对象，只能 Leave the fork network（脱离网络），这是单向操作，不能再连回去
  • 机密内容不要放进仍连着上游的 fork；删 fork 也清不干净网络里已经存在的 commit

一句话：upstream 可以拉你 fork 里已经推上去的代码，但不能把 fork 当自己的仓库随便改。 公开仓库上，「拉」几乎是默认能力；「写」才需要额外授权。

14. 删除、脱离与可见性

14.1 删除 fork

在 fork 仓库：Settings → General → 最底部 Danger Zone → Delete this repository。需要输入仓库全名确认。

删除 fork 会永久删掉依附在这个 fork 上的 Pull Request 和相关配置，不能恢复。贡献记录有可能仍出现在上游的历史上，但那条 PR 本身没了。还有未合的 PR 时，不要删 fork。

删除 fork 不会删掉你电脑上的 clone。本地目录还在，只是远程 origin 已经不存在。

14.2 脱离 fork 网络

想把这份代码变成和上游无关的独立仓库，可以 Leave the fork network（脱离 fork 网络）。之后不会再自动跟上游同步，也不能再连回去。这是公开 fork 上切断「Git 对象仍可能被上游读到」的办法，详见第 13 节。

脱离后不会保留原来的 Issues、PR、Wiki、Star、Watch、评论、子 fork 等元数据，Git 提交历史会保留。

14.3 上游被删或改可见性时

发生的事 fork 会怎样
私有上游被删除 它的私有 fork 一并删除
公开上游被删除 仍活跃的公开 fork 会成为这个网络新的上游
公开仓库改成私有 原来的公开 fork 仍公开，但进入另一个网络
私有仓库改成公开 私有 fork 仍私有，并拆到各自的私有网络

私有仓库若撤销了某人的访问权，此人对该私有仓库的 fork 会被删除；本地 clone 还在。你有责任确保失去访问权的人处理掉本地的机密内容。

公开 fork 不继承上游的权限结构，由 fork 主人自己管谁能写。但同一网络里的 Git 对象是共享的：推到网络中任一仓库的 commit，其他仓库（包括上游）仍可能读到。删了 fork，贡献过的代码仍可能留在网络里。

15. 常见问题

Q：Fork 和直接 Clone 上游有什么区别？

Clone 只是本地拷贝。没有写权限就推不上去。Fork 先在你名下建一个 GitHub 仓库，再 clone 这个仓库，git push 才推得到，也才能对上游开 PR。

Q：点了 Fork，电脑上为什么没有文件？

Fork 发生在 GitHub 上。还要 git clone 你的 fork，或使用 gh repo fork ... --clone=true。

Q：git push 提示权限不够？

多半 origin 仍指向上游，或你 clone 的是上游而不是自己的 fork。用 git remote -v 检查，origin 应是 github.com/你的用户名/仓库.git。

Q：Fork 提交和自己项目提交，命令到底差在哪？

git add、git commit 完全相同。差别在更新主分支时 fork 要 fetch upstream，推完还要向上游开 PR。完整对照见第 9 节。

Q：Fork 比上游旧很多，PR 里全是无关提交？

先同步 main（网页 Sync fork，或 git fetch upstream && git merge upstream/main），再把功能分支 rebase 或 merge 到最新的 main，然后推送。

Q：可以 fork 到公司组织吗？

可以，前提是你在该组织有创建仓库的权限。私有仓库还受套餐和 fork 策略限制，GitHub Free 组织不能接私有 fork。

Q：要不要把上游所有分支都拷过来？

给开源提 PR，勾选 Copy the DEFAULT branch only 即可，fork 更干净。确实需要其他分支，再在 Branches 页补。

Q：上游能随意拉取 fork 里的代码吗？

公开 fork 上，能读、能 clone，不需要你再授权；开不开 PR 都不影响「已经被 push 上去的代码能否被拉走」。上游默认不能往你的 fork 里随便 push。私有 fork 会继承上游权限，读甚至写都可能更宽。完整说明见第 13 节。

Q：删了 fork，已经合进上游的代码还在吗？

合进上游的提交还在上游。未合的 PR 会随 fork 一起消失。网络里的 Git 对象仍可能被其他 fork 看到。

Q：练习用哪个仓库？

用 octocat/Spoon-Knife。改坏了也不影响真实项目。

16. 小结

一次完整的贡献可以记成这条链：

  1. 网页或 gh repo fork 把仓库 fork 到自己名下
  2. git clone 你的 fork（不要只 clone 上游）
  3. git remote add upstream <上游地址>
  4. 从最新 main 拉出功能分支，改完 git push -u origin 分支名
  5. 在上游开 PR：base 是上游，compare 是你的 fork 分支
  6. 上游往前走了，就 Sync fork 或 git fetch upstream && git merge upstream/main && git push origin main

日常口诀：改自己的 origin，跟上游的 upstream，合代码靠 Pull Request。 git add / git commit 和自己项目一样；不一样的是先同步 upstream、推到 fork 的 origin，再向上游开 PR。推到公开 fork 的代码，上游默认就能读；往你的 fork 里写，才需要额外授权。

官方文档：Fork a repository、About forks、Syncing a fork、Creating a pull request from a fork、Allowing changes to a pull request branch created from a fork。
