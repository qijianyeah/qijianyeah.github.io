Dify 入门完全指南：本地部署、模型接入与第一个工作流

Dify 是面向 LLM 应用开发的开源平台。它把模型供应商、提示词、知识库、工作流、应用发布与 API 集成放到同一套产品界面中：非开发者可以用可视化方式搭建应用，开发者则可以把工作流和模型能力接入现有系统。

本文从平台定位开始，完成一次基于 Docker Compose 的本地部署，再搭建一个“开始 → LLM → 结束”的最小工作流。

1. Dify 是什么

Dify 可以理解为一套 LLM 应用开发平台：它不负责训练基础模型，而是把“调用模型、组织上下文、处理输入输出、编排业务流程、对外发布应用”这些重复工作产品化。

典型能力包括：

能力 作用
模型供应商管理 统一配置 LLM、Embedding、重排序、语音等模型凭据
Prompt 与应用编排 用应用或工作流组织提示词、变量和输出
RAG / 知识库 处理文档、分段、向量检索与引用
工作流节点 用开始、LLM、代码、条件、迭代、工具等节点实现逻辑
API 与发布 把应用能力以 Web 应用或 API 的形式交付

从工程视角看，Dify 接近“面向生成式 AI 的 BaaS（Backend as a Service）”：平台封装了大量基础设施，团队可以把精力集中在业务数据、流程设计、提示词和评测上。

BaaS 的核心价值不是取代业务后端，而是把用户鉴权、数据存储、任务调度、接口接入等通用能力服务化。Dify 则把其中与 LLM 应用最相关的那部分能力进一步封装。

2. 部署前准备

官方 Docker Compose 快速部署要求至少具备：

项目 建议
CPU 不低于 2 核
内存 不低于 4 GiB；本地 Docker Desktop 通常建议分配更多内存
Docker Linux Docker 19.03+ 或 Docker Desktop
Docker Compose 2.24.0+
工具 git、curl；按官方“拉取最新发布版”命令还需要 jq

2.2 镜像拉取问题

不要把某个第三方镜像站当成永久可用的固定配置。镜像源的可用性和合规状态会变化；拉取失败时优先：

  1. 检查网络、DNS、代理与 Docker Desktop 状态；
  2. 使用企业已批准的镜像仓库或镜像代理；
  3. 查看 Dify 官方部署 FAQ 与当前发布说明；
  4. 避免把不明来源的镜像配置直接用于生产环境。

5. 配置模型供应商

Dify 应用必须至少有一个可用模型。进入 Integrations（集成）→ Model Provider（模型供应商），安装所需供应商插件后，输入 API Key 或其他凭据。

常见模型类别：

类别 常见用途
LLM / 系统推理模型 聊天、生成、分类、总结、工作流 LLM 节点
Embedding 文档向量化、知识库检索、语义召回
Rerank 对初步检索结果按相关性重新排序
Speech-to-Text 语音转文本
Text-to-Speech 文本转语音

配置时注意：

  • 凭据通常对工作区可用，管理员应按最小权限与成本边界管理；
  • 新模型或微调模型未出现在预置列表时，是否可添加取决于供应商插件能力；
  • Dify 的供应商与模型通过插件体系演进，具体页面名称、支持模型和参数会随版本变化，以当前产品界面和官方文档为准。

8. Dify 与 Coze 如何选择

Dify 和 Coze 都能构建 AI 应用，但不应把它们简单视为可互换工具。产品能力、定价、部署方式和区域可用性会持续变化，选型应回到实际约束。

维度 更适合优先考虑 Dify 的情形 更适合优先考虑 Coze 的情形
部署与数据 希望自托管、接入内部网络或受合规约束 更偏好云端托管、降低基础设施运维
工程集成 要接入现有业务 API、知识库与发布流程 希望快速做面向用户的 Bot 或内容原型
可定制性 需要细粒度工作流、模型或插件定制 需求以平台现成功能为主
使用门槛 有开发 / AI 工程支持 产品、运营、内容团队希望快速上手

实际选择时，先回答四个问题：

  1. 数据能否出网，是否要求私有化部署？
  2. 需要对接哪些内部系统与模型供应商？
  3. 谁负责后续运维、版本升级、观测与成本控制？
  4. 是验证一个轻量原型，还是建设长期运行的生产应用？

9. 小结

完成本篇后，你应该已经走通了这条最小路径：

下一步可继续学习文档提取、代码节点、迭代节点与结构化输出，把简单问答工作流升级为可处理真实业务数据的应用。
