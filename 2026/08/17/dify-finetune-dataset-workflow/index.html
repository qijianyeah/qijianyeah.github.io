Dify 工作流实战：从文档生成大模型微调 JSONL 语料

高质量微调数据往往比“把模型训起来”更难获得。本文使用 Dify 工作流，把用户上传的文档转换为可供人工审核的问答候选，再输出 JSONL 格式的对话样本。

需要先明确边界：Dify 工作流生成的是合成语料候选，不等于完成微调，更不等于数据天然可用。 它适合降低初始整理成本，但最终仍需要去重、事实校验、版权与隐私审查、格式验证和训练集 / 验证集划分。

1. 微调与 JSONL 数据格式

微调（Fine-tuning）是在预训练模型基础上，用特定任务或领域的数据继续训练，使模型更稳定地遵循某种表达方式、任务结构或知识边界。

一个完整微调项目通常包含：

  1. 明确任务与评价指标；
  2. 采集或整理合法的数据；
  3. 清洗、去重、脱敏、标注与质量控制；
  4. 按训练集、验证集、测试集划分数据；
  5. 执行训练并评测；
  6. 部署、监控与持续迭代。

本文覆盖其中的“从文档生成候选监督样本”环节。

1.1 为什么常用 JSONL

JSONL（JSON Lines）要求每行都是一条独立、完整的 JSON 对象，适合流式处理、分批追加与训练管线读取。

1.2 合成数据的质量风险

LLM 可以快速根据文档生成问答，但也可能：

  • 编造原文不存在的事实；
  • 把推测写成确定结论；
  • 重复生成同义问题；
  • 泄露原文中的个人信息、商业秘密或受版权保护内容；
  • 生成不符合目标模型训练格式的 JSON。

因此，下游应把每条记录视为“待审核候选”，而不是直接投喂训练。

3. 开始节点：接收文件与任务约束

开始节点负责暴露用户输入。建议至少设置：

变量 类型 用途
attachments 文件或文件列表 用户上传待处理文档
system_prompt 短文本 目标模型的系统提示词 / 风格约束
questions_per_chunk 数字 每个文本分块生成的问答数量
domain 短文本 领域标签，如“医疗科普”“产品手册”

原始课程示例中为文件与系统提示词设置了输入。实际项目里不要把“48 字符限制”等界面细节当成稳定契约；节点字段和限制会随 Dify 版本变化，应以当前产品界面为准。

开始节点还应做业务层约束：

  • 明确允许上传的文件类型和大小；
  • 告知用户不要上传敏感个人信息与无授权材料；
  • 对文档来源记录任务 ID、上传时间、操作者与许可状态；
  • 大文件和多文件任务采用异步 / 批处理策略。

4. 文档提取器：把文件变成文本

LLM 节点不能直接读取文件变量；文档提取器负责把上传文件转换为下游可引用的文本变量。

当前 Dify 文档说明，文档提取器支持单文件或批量文件：

输入 输出
单个文件 string 类型文本
多个文件 array[string] 类型文本数组

将开始节点的 attachments 连接到文档提取器后，后续节点应引用其 text 输出，而不是直接引用原始文件对象。

4.1 文件格式不是永远都能直接处理

不同 Dify 版本、部署配置与文件格式会影响解析能力。尤其是旧格式 Office 文件、扫描 PDF、演示文稿等，可能需要额外解析服务或 OCR 流程。

建议在生产前建立一组真实样本做验收：

  1. 正常 PDF、DOCX、TXT、Markdown；
  2. 扫描件与图片型 PDF；
  3. 超长文档；
  4. 多语言文档；
  5. 表格、代码、公式较多的文档。

5. 代码节点：清洗和分块，而非盲目截断

课程原始工作流通过代码节点合并文本后截取前一部分字符，再交给 LLM。

这种方式能快速跑通 Demo，但存在两个问题：

  1. 只截取开头会系统性丢失文档后半部分内容；
  2. 字符数、Token 数和语义边界并不等价，硬截断可能切断句子、代码块或表格。

6. LLM 节点：生成可审核的问答

LLM 节点接收一个文本块、系统提示词和生成约束，并输出 JSONL 候选。

6.2 输出数量不要只靠“每次 10 条”

固定要求每块生成 10 条，容易在信息稀疏的文本上逼迫模型重复或臆造。更合理的方式是：

  • 允许模型在“内容不足”时少生成；
  • 设置最大条数而不是必须条数；
  • 为定义、步骤、对比、边界条件、常见误区等问题类型设配额；
  • 记录样本来自哪个文件、哪个分块，便于回溯。

7. 结束节点与 JSONL 输出

结束节点将 LLM 输出作为工作流结果返回。

如果 LLM 输出变量是 text，结束节点通常直接引用对应文本变量即可。重点是不要让结束节点混入调试信息、标题或自然语言解释，否则下游 JSONL 校验会失败。

8. 测试、校验与人工审核

运行工作流时，用一份可公开、篇幅较短的测试文档验证流程。

输出结果应是连续的 JSONL 记录：

8.1 三层验收

层级 检查内容
格式 每一行可被 json.loads 解析；role 顺序正确；字段齐全
内容 问答可回溯到源文档；无明显幻觉、重复、矛盾与敏感信息
训练适配 与目标模型微调 API 的格式、最大长度、特殊 token 和许可要求一致

8.2 抽样审核问题清单

对每一批样本，至少抽查：

  1. 问题是否能从原文得到回答？
  2. 答案是否引入原文没有的细节？
  3. system 提示词是否符合目标用途？
  4. 同一主题是否生成了重复问题？
  5. 是否包含手机号、地址、身份信息、账号、商业机密等内容？
  6. 文档是否具备被用于训练的授权？

9. 生产化改进建议

9.1 加入迭代与合并

大文件不要只处理第一个分块。使用迭代节点逐块生成，再把结果合并为一个 JSONL 文件或写入数据存储。

9.2 引入结构化输出与重试

仅靠 Prompt 不能保证百分之百输出合法 JSON。可使用平台提供的结构化输出能力（若当前模型 / 版本支持），或增加“JSON 解析失败 → 修复节点 → 再校验”的回路。

9.4 把“微调”与“RAG”分开选择

当需求是让模型回答频繁变化的企业知识时，RAG 通常比微调更适合；当目标是固定风格、格式遵循、特定任务模式时，微调才可能更匹配。两者也可以组合，但不能用“让模型记住一篇文档”作为唯一判断标准。

10. 小结

用 Dify 生成微调语料的核心链路是：

工作流降低的是第一轮数据整理与问答生成成本；决定最终训练效果的，仍然是数据授权、事实准确性、覆盖度、多样性、去重、审核和评测。
