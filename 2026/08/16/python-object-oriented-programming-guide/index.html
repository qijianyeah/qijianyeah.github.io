1. 从编程思维说起：面向过程与面向对象

面向过程和面向对象不是互相排斥的两种语言特性，而是组织程序的两种思维方式。

  • 面向过程关注“完成任务需要哪些步骤”，适合流程清楚、规模较小的问题。
  • 面向对象关注“系统中有哪些角色，各自保存什么状态、承担什么职责”，适合状态丰富、角色较多、需要持续扩展的系统。

二者最终都要落实为具体步骤。面向对象负责划分边界和职责，对象内部的方法仍然由一条条语句实现。实际开发中应根据问题规模选择合适的组织方式，不必为了“面向对象”而把每个函数都包装成类。

对比维度 面向过程 面向对象
关注点 执行步骤与数据流 对象、状态、职责与协作
常见组织单元 函数、模块 类、对象、方法
适合场景 简单脚本、线性流程 复杂业务、长期演进的系统
主要优势 直接、容易理解 封装边界清晰，便于复用和扩展
主要风险 状态分散时维护困难 设计过度会增加抽象成本

Python 是多范式语言。一个程序可以同时使用面向过程、面向对象和函数式风格，关键是让代码结构服务于问题本身。

2. 类、对象与“一切皆对象”

2.1 类与对象的关系

类是对一组对象共同特征和行为的抽象；对象是由类创建出来的具体实例。例如，“学生”可以是类，每名具体学生则是对象。

类通常包含两类成员：

  • 属性：描述对象或类的状态，例如姓名、年龄、学校。
  • 方法：描述对象或类能够执行的行为，例如学习、修改学校。

类不是现实事物的完整复刻，而是针对当前问题保留有用的信息。同一个人放在教务系统中可能关注学号和课程，放在健康系统中则可能关注身高和体重。

2.2 Python 中一切皆对象

在 Python 中，数字、字符串、容器、函数、类和模块都以对象形式存在。因此它们都可以被变量引用、作为参数传递，也可以接受 id() 和 type() 的检查。

函数可以作为参数传递，类也能赋给变量，这些能力正是“一切皆对象”的直接体现。

2.3 id、type 与 value

理解对象时，可以从身份、类型和值三个角度观察：

  1. 身份（identity）：对象在一次运行期间的唯一标识，可用 id(obj) 查看。CPython 常将它实现为内存地址，但语言规范只保证其在对象生命周期内唯一，因此不应依赖具体数值。
  2. 类型（type）：决定对象支持哪些操作，可用 type(obj) 查看。
  3. 值（value）：对象表达的数据内容。

== 通常比较值，is 比较是否为同一个对象。除 None 等单例判断外，不要用 is 代替值比较。

7. 封装与名称改写

7.1 封装的目标

封装不是简单地“把属性藏起来”，而是让对象自己维护内部状态和约束，只向外暴露稳定、易用的接口。调用者不需要知道实现细节，类也能在不破坏调用代码的前提下调整内部实现。

Python 常见的可见性约定是：

  • name：公开成员。
  • _name：约定为内部成员，外部代码不应随意依赖。
  • __name：触发名称改写，主要用于避免子类意外覆盖。

7.3 双下划线是名称改写，不是真正私有

属性名以两个下划线开头、但不以两个下划线结尾时，Python 会进行名称改写：

__balance 在类外通常表现为 _Account__balance。这并不是安全边界，也不能阻止有意访问；它的主要用途是减少继承体系中的命名冲突。真正的封装依赖清晰接口、团队约定和合理设计，而不是依赖双下划线实现访问控制。

8. 继承、重写与方法解析顺序

8.1 继承表达 is-a 关系

继承让子类复用并扩展父类行为，适用于稳定、合理的 is-a 关系：学生是人，狗是动物。若只是“使用某项能力”，组合通常比继承更合适。

继承具有传递性。如果 GraduateStudent 继承 Student，它也会间接继承 Person 和 object 的能力。

8.2 super() 与方法重写

子类定义与父类同名的方法称为重写。子类可以完全替换父类实现，也可以使用 super() 延续继承链上的下一个实现：

super() 并不简单等同于“调用父类”。它会按照当前类的方法解析顺序（MRO）寻找下一个实现，这一点在多继承中尤其重要。

8.3 isinstance() 与 issubclass()

  • isinstance(obj, Class) 判断对象是否为某个类或其子类的实例。
  • issubclass(Sub, Base) 判断一个类是否为另一个类或其子类的派生类。
  • 两者的第二个参数都可接收类型元组，表示匹配其中任意一个。

需要类型判断时优先使用 isinstance()，而不是 type(obj) is Class，因为前者能正确处理继承。

8.4 多继承与 MRO

Python 支持多继承。若多个父类提供同名方法，Python 使用 C3 线性化算法计算 MRO，并按该顺序查找：

Child 的查找顺序是 Child -> Left -> Right -> Root -> object。由于各层都使用协作式 super()，菱形继承中的 Root.process() 只会执行一次。

设计多继承时应遵循：

  1. 所有协作方法都使用 super()，不要直接写死某个父类名。
  2. 同一调用链中的方法签名应兼容。
  3. 使用 Class.mro() 或 Class.__mro__ 检查解析顺序。
  4. 优先把职责单一、状态较少的能力设计为混入类（mixin）。
  5. 当继承关系难以解释时，优先考虑组合。

9. 多态与鸭子类型

9.1 同一接口，不同行为

多态意味着调用方使用统一操作，不同对象提供各自行为：

announce() 不需要用条件分支判断每一种动物。新增一个实现了 speak() 的类型时，它也无需修改。

9.2 鸭子类型不依赖继承

“如果一个对象走起来像鸭子、叫起来也像鸭子，就把它当作鸭子使用。”这句话强调的是行为兼容，而不是继承关系。

Robot 没有继承 Dog、Cat 或共同父类，但它提供了调用方需要的 speak()，因此可以参与同一套逻辑。鸭子类型让代码保持低耦合，但接口契约仍应通过命名、文档、类型注解和测试表达清楚。

双下划线开头并结尾的名称常被称为“魔术”或“特殊”名称。它们对应 Python 数据模型中的标准协议，不应随意创造新的双下划线名称。

10.3 不要依赖 del() 释放资源

del variable 删除的是一个名称绑定，不保证对象立刻销毁。对象可能仍有其他引用，也可能处于引用环中；不同 Python 实现和解释器退出阶段的最终化时机也不一致。因此，不应依赖 __del__() 关闭文件、连接或锁。

11. 抽象类：用接口约束实现

鸭子类型强调灵活，抽象基类则适合需要明确继承体系和强制接口的场景。标准库 abc 提供 ABC 和 abstractmethod：

包含未实现抽象方法的类不能实例化。抽象类本身可以包含普通方法，甚至可以为抽象方法提供默认实现；子类是否需要调用该实现取决于具体契约。

抽象类、鸭子类型和 Protocol 的侧重点不同：

方案 是否要求继承 是否运行时阻止实例化 适用场景
鸭子类型 否 否 简单、动态、低耦合协作
Protocol 否 否 结构化接口与静态类型检查
ABC 是 是 明确的继承体系和强制实现约束

不要因为“接口看起来更正式”就为每个类创建抽象父类。只有当多个实现确实共享稳定契约，并且运行时约束有价值时，抽象类才值得引入。

12. 学习总结与实践建议

Python 面向对象的核心不是记住装饰器和双下划线名称，而是建立清晰的职责边界：

  1. 从对象的状态和行为出发建模，简单流程不必强行设计成类。
  2. 用实例属性表达对象独立状态，用类属性表达真正共享的数据。
  3. 根据所需上下文选择实例方法、类方法或静态方法，不把静态方法当作性能优化手段。
  4. 通过公开接口和 property 维护不变量，理解双下划线只是名称改写。
  5. 继承只用于合理的 is-a 关系；多继承必须理解 MRO，并使用协作式 super()。
  6. 用多态和鸭子类型减少对具体类型的依赖，必要时用 Protocol 或抽象类明确契约。
  7. 把魔术方法视为协议入口，遵守 Python 数据模型，不依赖 __del__() 的触发时机。

练习时可以从一个小型课程管理系统开始：先定义学生和课程，再逐步加入属性校验、继承、多态、可迭代课程名单和上下文管理。每增加一个抽象，都问自己两个问题：它解决了什么变化？它是否让调用方更简单？能持续回答这两个问题，才算真正掌握面向对象设计。
