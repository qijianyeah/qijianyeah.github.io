一、重试机制概览

Dubbo 的重试机制是集群容错能力的核心：当一次 RPC 因网络抖动、节点临时不可用等原因失败时，自动换节点再试，提升最终调用成功率。

它是一把双刃剑——用得好提升可用性，用不好会造成重复写入、重复扣款等脏数据。

1.1 关键概念

概念 说明
默认策略 failover（失败自动切换），默认 retries=2，共最多调用 3 次
触发条件 Consumer 端 invoke 抛出非业务 RpcException / 其它 Throwable（超时、网络等）
不触发条件 正常返回 Result（含业务错误码、null、甚至 Provider 异常封装在 Result 里）
适用场景 幂等操作（读、删除等）
禁用场景 非幂等写操作（新增、更新、扣减库存）

重试发生在 Cluster 层（默认 FailoverClusterInvoker），不是业务代码自己循环。只有 Cluster 层捕获到「抛出的异常」才会进入下一轮；业务 POJO 返回值本身从不触发原生重试。

二、Failover 集群详解

2.1 是什么

Failover 是 Dubbo 默认集群容错策略（Cluster.DEFAULT = "failover"）：调用失败后自动切换到其它 Provider 再试，用重试换更高可用性。代价是延迟变长，且可能重复执行，因此非幂等接口要慎用。

入口类 FailoverCluster 只负责创建 Invoker：

真正执行重试逻辑的是 FailoverClusterInvoker。

2.2 在调用链中的位置

多个 Provider 由 Directory 维护；Cluster 决定「失败了怎么办」。Failover 的答案是：再选别的试。

2.3 行为要点

  1. 先调一次，失败再重试（默认 retries=2 → 最多 3 次）
  2. 重试前会 重新 list Provider，再负载均衡，并尽量避开已失败节点（invoked 列表）
  3. 业务异常不重试（RpcException.isBiz() == true）
  4. 全部失败后抛出汇总 RpcException；中途成功则返回（若之前失败过会打 warn）

方法级关闭重试：

一句话：failover = 失败自动切换 Provider 重试；适合读多、可幂等的调用。

三、核心工作流程

默认 failover 的重试流程可以概括为四步：

  1. 发起调用：负载均衡选择一个 Provider 发起 RPC。
  2. 捕获异常：若 invoke 正常返回 Result，流程结束（即使 Result 里带业务异常 / 错误码，也不重试）；若 抛出非业务异常，进入重试。
  3. 循环重试：按 retries 再试（总次数 = retries + 1）。
    • 每次重试前重新获取最新可用 Provider 列表。
    • 通过负载均衡重新选择节点，尽量避开已调用过的故障节点。
  4. 返回结果：某次成功则返回；全部失败则抛出汇总异常。

retries 是额外重试次数，不含第一次。retries=2 表示最多调用 3 次。

例如 timeout=1000ms、retries=2，最坏约 3 秒。超时配太长时，重试会把延迟成倍放大。

四、什么时候会触发重试

理解触发条件，关键看 FailoverClusterInvoker.doInvoke 的判定，而不是「业务上算不算失败」。

4.1 会触发重试

情况 说明
TimeoutException / 调用超时 最常见，Consumer 端抛 RpcException.TIMEOUT_EXCEPTION
网络异常（连接断开、发送失败等） 抛 RpcException.NETWORK_EXCEPTION
序列化等框架异常 抛对应 code 的 RpcException
其它非 biz 的 RpcException e.isBiz() == false 时进入下一轮
其它 Throwable 被包装成 RpcException 后进入下一轮

前提：当前使用 **cluster=failover**（默认），且 retries > 0（默认 2）。

4.2 不会触发重试

情况 说明
业务返回值（如 code=500、null） 通信成功，返回了正常 Result
Provider 抛出业务异常并封装进 Response Consumer 侧通常拿到 Result.hasException()==true，Cluster 层直接 return，不重试
RpcException 且 isBiz()==true 立即抛出，终止重试
retries=0 或最终算出调用次数 ≤ 1 只调一次
使用 failfast / failsafe 等策略 根本不走 failover 重试逻辑

4.4 用日志快速区分

会触发重试的特征：

不会触发重试的特征：

  • 只有业务错误码（如 code=1001），没有上述框架异常栈
  • Provider 异常已作为响应内容返回，Consumer 代理在 Cluster 之后才 recreate() 抛给业务代码

4.5 陷阱一：服务端捕获异常后返回 POJO

Dubbo 拿到完整业务对象，认为调用成功，绝对不会重试。

4.6 陷阱二：Provider「直接抛异常」就会重试？

通常不会。 Provider 未捕获异常一般会进入响应的 exception 字段，Consumer 的 DubboInvoker 正常返回带异常的 Result。FailoverClusterInvoker 看到的是成功的 return result，不会进入 catch，因而不会重试。异常往往在更外层代理 Result.recreate() 时才抛给业务线程——此时重试窗口已过。

真正让 failover 重试的，是 Consumer 调用链路在 Cluster 层就抛出的超时、网络等异常。详见 7.3。

五、多种容错模式

通过 cluster 属性配置。不同模式的「失败后行为」完全不同。

模式 (cluster) 行为描述 重试逻辑 适用场景
failover（默认） 失败后自动切换其它 Provider 同步循环重试 retries 次 读操作等幂等场景
failfast 只调一次，失败立即报错 不重试 非幂等写操作
failsafe 失败后忽略异常，记日志 不重试 审计日志等旁路
failback 失败后后台定时异步重发 异步定时重试 消息通知等非实时
forking 并行调多个，一个成功即返回 并行，无串行重试 高实时读（更耗资源）
broadcast 广播所有 Provider 无串行重试 通知所有节点更新缓存等

只有 **failover**（以及自定义 Cluster）才会按本文所述做「失败切换重试」。把 retries 配在 failfast 上没有意义。

6.5 配置优先级与注意点

结合源码还需注意：

  1. FailoverClusterInvoker 读的是 directory.getConsumerUrl() 上的 retries，因此应在 Consumer 侧配置才能稳定生效。
  2. URL 合并时 Consumer 参数会覆盖 Provider 同名参数（DefaultProviderURLMergeProcessor：先放 Provider，再 putAll Consumer）。所谓「Provider 配置一定优先」并不准确。
  3. Provider 上写 retries 更多是「约定 / 文档化」；真正驱动 failover 次数的，是 Consumer URL / RpcContext。

七、进阶：按返回值重试

需求：RPC 返回 null 或业务错误码（如 code=10001）时，也要自动再试几次。

核心事实：Dubbo 原生 retries 只认 Cluster 层抛出的非业务异常，不支持按业务返回值重试。

7.3 Provider 抛异常为何通常不重试

网上常见误区：

对照 FailoverClusterInvoker：

  • Provider 异常 → 多半装进响应 → Consumer invoke 返回 Result（hasException()==true）
  • Cluster 层 不会 catch，也就 不会重试
  • 之后代理 recreate() 才把异常抛给业务代码——此时重试窗口已过

若抛的是 new RpcException(RpcException.BIZ_EXCEPTION, ...) 且该异常在 Cluster 层被抛出，则 isBiz() 为 true，更不会重试。

做法 能否触发原生 failover
Provider 返回错误码 / null 否
Provider 抛业务异常（进 Result） 否（通常）
Provider 抛 RpcException(BIZ_EXCEPTION) 且在 Cluster 抛出 否
Consumer 超时 / 网络失败 是
Consumer 手动重试 / 自定义 Filter 按返回值再调 是（应用层实现）

「按返回值重试」请用 7.1 / 7.2，不要依赖「Provider 抛个异常让框架重试」。

九、最佳实践与避坑

9.1 推荐做法

实践 说明
读操作开重试 查询等幂等操作可用默认 retries=2
写操作关重试 cluster="failfast" 或 retries="0"
在 Consumer 配置 retries 与 FailoverClusterInvoker 读 consumerUrl 的行为一致
合理设超时 总耗时上界约 timeout × (retries + 1)
按返回值重试用业务 / Filter 不要幻想 Provider 抛异常就能走原生 retries

9.2 避坑指南

陷阱 后果 解决方案
非幂等写开重试 重复插入、重复扣款 failfast + retries=0
重试次数过大 延迟暴涨、雪崩 retries ≤ 2，配合超时
超时设太长 重试总耗时成倍放大 timeout 宜紧（如 1s 级，按业务调）
捕获异常改返回错误码 本可失败的调用变「成功」 需要框架重试就别吞掉超时 / 网络类失败；要按值重试用 Filter
以为 Provider 抛异常会 failover 实际不重试 改用 Consumer 重试或 Filter
RpcContext 传字符串 retries 配置静默无效 传 Number
Filter 重试 + failover 叠加 调用次数爆炸 统一策略，算清上限

9.3 配置速查

场景 推荐配置 示例
查询（幂等） failover + retries=2 默认即可
删除（幂等） failover + retries=1 retries="1"
新增 / 更新（非幂等） failfast + retries=0 cluster="failfast" retries="0"
通知 / 日志 failsafe cluster="failsafe"
异步通知 failback cluster="failback"

十、总结

知识点 核心要点
Failover 默认集群策略：失败切换 Provider，同步重试
触发条件 Cluster 层抛出非 biz 异常（超时、网络等）
不触发 业务返回值、Result 内封装的 Provider 异常、isBiz()
默认次数 retries=2 → 最多 3 次
配置 优先 Consumer 方法 / 接口级；RpcContext 需 Number
按值重试 原生不支持 → 手动循环或自定义 Filter
源码入口 FailoverClusterInvoker.doInvoke()
原则 幂等是重试前提，写操作务必关掉

先分清「框架失败」和「业务失败」，再决定用 failover、failfast，还是自己按返回值重试——这是用好 Dubbo 重试机制的关键。
