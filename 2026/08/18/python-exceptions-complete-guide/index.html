业务逻辑本身很简单，真正让程序「挂掉」的是运行时错误事件——异常。

2. 什么是异常

异常（Exception）是程序运行时发生的错误事件，会打断正常执行流程。一旦产生且未被处理，解释器通常会打印堆栈信息，然后终止当前程序。

可以把它理解成：

  1. 某行代码触发了错误条件
  2. 解释器创建对应的异常对象
  3. 沿着调用栈向上寻找能处理它的 except
  4. 找不到就让程序异常退出

常见触发源包括：非法输入、除零、下标越界、文件不存在、网络超时、类型不匹配等。

这种写法能挡住一部分非法输入，但有明显缺点：

  1. 代码臃肿：业务与防护逻辑缠在一起
  2. 可读性差：层层嵌套，主流程被淹没
  3. 维护成本高：每加一种校验就多一层分支
  4. 很难堵全：例如 isdigit() 不接受负数 -3，也不覆盖所有 int() 能失败的情况

结论：简单前置校验可以有，但系统性错误处理应交给异常机制。

5. 异常类的继承体系

Python 内置异常是一棵继承树。开发中最常接触的是 Exception 及其子类；KeyboardInterrupt、SystemExit 等直接挂在 BaseException 下，一般不要用裸 except: 或 except Exception 去「吞掉」它们。

12. 自定义异常

内置异常覆盖了大多数语法/运行时错误，但业务规则往往需要自己的异常类型，例如：

  • 用户年龄必须大于 18
  • 密码长度必须大于 6
  • 余额不足不能转账
  • 商品库存不足不能下单

自定义异常应继承 Exception（或其合适子类），类名通常以 Error 结尾，并保持简单：携带必要属性，方便上层提取信息。

设计建议：

  1. 按业务域划分异常，如 InsufficientBalanceError、OutOfStockError
  2. 需要区分处理时再细分类型；不要为每个细枝末节都建一个类
  3. 捕获时优先写具体自定义类型，而不是一律 except Exception

13. 异常的传递

如果当前代码块没有捕获异常，它会沿着调用链向上传递；每一层都有机会处理。若一直无人处理，程序最终因未捕获异常而终止。

14. 实践建议小结

  1. 先定位再处理：看异常类型与堆栈最后几帧
  2. 捕获要具体：优先 ValueError、ZeroDivisionError 等，慎用裸 except:
  3. 业务与防护分离：用 try-except 代替层层 if 堵漏洞
  4. 成功路径放 else，清理放 finally / with
  5. 规则校验用 raise，领域规则用自定义异常
  6. **日志用 traceback**，不要只打印一句「出错了」
  7. 异常会向上传递：在合适的那一层处理，既不要过早吞掉，也不要全部堆到最顶层

把「求商」这个例子吃透后，文件读写、网络请求、Web 接口里的错误处理，都是同一套机制的延伸。
